## Generic SQL and resource policy (`m2-sqlite.v1`)

New connection per query, `:memory:` only, no URI/file/client-selected connection. Load trusted fixture using parameter values before allowing untrusted SQL. Set/verify `query_only=ON`, `trusted_schema=OFF`, `temp_store=MEMORY`; never register UDFs, virtual tables or extensions. Extension loading remains disabled; if supported explicitly disable it. Set and verify SQLite `hard_heap_limit` ≤8,388,608 bytes and >0 before query execution; this bounds SQLite's allocator within this private Worker, not total Python/isolate memory. If a mandatory control is missing/ineffective, return `runtime_incompatible` without executing untrusted SQL.

Allow one statement passed unchanged to `Connection.execute`; first non-whitespace token must be SELECT or WITH (leading comments are unsupported); never use executescript or SQL rewriting. Deny-by-default authorizer returns DENY, not IGNORE: allow only SELECT, READ of database `main`, table `sales`, one declared column or the empty count(*) column, and FUNCTION names `sum,count,min,max,avg,abs,round,coalesce,nullif,lower,upper,length,substr,like,strftime,row_number,rank,dense_rank,lag,lead`. Require at least one authorized sales READ. Deny recursive CTE actions; writes/DDL/transactions/PRAGMA/ATTACH/DETACH, internal `sqlite_master`/`sqlite_schema`/temp reads, unrelated tables, blobs, file/network/extension/unknown functions and every other action deny. CTE/subquery/group/rank/date arithmetic is general SQL within these capabilities; successful execution never proves question meaning.

SQLite can report a bare `COUNT(*)` as an empty-column READ without database identity. Such a read proves the physical source only when SQLite reports database `main`; generated SQL should qualify `main.sales` or count a declared sales column so the callback proves the table, column and database together. An ambiguous empty-column read with `database=None` never increases the source audit or passes source authorization; this also prevents a same-named CTE from masquerading as the fixture.

Apply/verify connection limits: SQL_LENGTH 8,000 bytes; LENGTH 65,536 bytes; COLUMN 16; EXPR_DEPTH 30; COMPOUND_SELECT 8; VDBE_OP 10,000; FUNCTION_ARG 8; ATTACHED 0; LIKE_PATTERN_LENGTH 128; VARIABLE_NUMBER 0; TRIGGER_DEPTH 0. These are reviewed conservative M2 policy caps, not throughput/latency promises. Install a progress handler every 100 VM instructions; abort on the 500th callback (at most approximately 50,000 executed VM instructions) or elapsed monotonic time ≥250 ms when measurable. VM counting is mandatory even where runtime clocks do not advance reliably. Parsing/compilation is additionally limited by input/depth/VDBE/heap caps. No thread/timer/process-based termination assumption. Always close connection; catch specific SQLite/input/resource errors and preserve safe classifications.

`max_rows` is a strict integer 1–20 for executable M2 intents (the broader M1 proposal permits 1–1000 and grants no runtime entitlement). Fetch at most max_rows+1 rows and refuse the entire result on overflow; do not publish a partial successful receipt. Maximum 16 unique column labels, each ≤64 UTF-8 bytes, and each TEXT cell ≤256 UTF-8 bytes. Refuse blobs, non-finite REALs, duplicate/unbounded column labels and unsupported values. Serialized query result ≤16,384 UTF-8 bytes; no whole-result buffering beyond those bounded cells/rows. Overflow/SQLite memory or integer-aggregate overflow produces an explicit result/execution error, not truncation or a default number.

## Python interface and exact receipts

All JSON object contracts are strict, extra-forbid, version literal string **"1"**; reject unknown versions, omitted required nullable fields and nonmatching types. Python validates Pydantic models at its boundary; TS validates the same golden payloads at its boundary. Do not pass arbitrary raw dictionaries through analytical layers.

Private service endpoints: GET `/health` → `version, python_version, sqlite_version, engine_policy, runtime_mode, build_revision, worker_version_id` (actual observed runtime; unsupported capability reports `runtime_incompatible`); GET `/metadata` → authoritative sales identity/schema/meanings/profile/capabilities/limits; POST `/query` → `{version, job_id:<UUID>, intent:<SqlIntent>}`. Intent identity is injected by the authorized Agent from `/metadata`, never taken from a model/client. Preserve exact nonblank `question` ≤2,000 characters and SQL ≤8,000 bytes. Adapter reads the body incrementally and refuses >16,384 bytes before JSON/Pydantic parsing. The outer Worker never forwards proof authorization/cookies or secret headers; binding possession grants this narrow synthetic-data service capability only.

Runtime provenance: `runtime_mode:"local"|"deployed"` is explicit server configuration, never inferred from absent metadata or client input. In deployed mode, `worker_version_id` is the UUID from the private Python Worker's `env.CF_VERSION_METADATA.id`; configure that actual version-metadata binding. `build_revision` is an injected `BUILD_REVISION` containing the exact lowercase 40-hex committed Git revision whose reviewed tree was packaged, captured by the reproducible build/deploy step. Missing/malformed deployed values fail startup/proof closed; never default to `unknown`, a fabricated UUID or current working-tree HEAD. Local mode permits worker_version_id=null and build_revision=null for an unmanifested/dirty development build, explicitly labeled local; an identified clean local build may supply its measured build revision. Local provenance is never deployed acceptance. Capture active deployment-object IDs separately from Wrangler/provider deployment receipts and map them to version UUIDs/main/head in the milestone report; do not rename one as the other.

`Metadata{version:"1",source:<SourceIdentity>,schema_revision,table:"sales",fields:[{name,sql_type:"TEXT"|"INTEGER",nullable:false,meaning:<bounded string>}],profile:{record_count:6,date_min:"2026-01-02",date_max:"2026-02-28",statistics:"exact"},capabilities:["query"],dialect:"sqlite",engine_policy,limits,runtime}`. `limits` uses named fields `max_sql_bytes:8000,max_rows:20,max_columns:16,max_column_bytes:64,max_text_bytes:256,max_result_bytes:16384,progress_interval:100,max_progress_callbacks:500,query_deadline_ms:250,sqlite_heap_bytes:8388608,sqlite_limits:<the declared per-connection categories/values>`. `QueryResult` success fields: `version, receipt_id:<UUID>, job_id:<same request UUID>, source:<verified SourceIdentity>, schema_revision, engine_policy, actual_sql:<exact executed text>, sql_sha256:<UTF-8 digest>, columns:<ordered labels>, rows:<ordered arrays of Cell>, row_count:<0..20>, result_sha256, coverage:"complete_query_result", truncated:false, analytical_validated:false, limits:<declared policy>, runtime:{python_version,sqlite_version,runtime_mode,build_revision,worker_version_id}`. Digest result content `{columns,rows}` using UTF-8 JSON with recursively sorted object keys, no whitespace, `ensure_ascii=False`, no NaN; shared Python/TS golden tests establish canonical parity. Metadata and result hashes identify bytes, not truth or authority. SQL without ORDER BY has unspecified row order; ranking queries must request explicit stable order for reproducible receipts.

`Cell` discriminated values: `{type:"integer",value:<canonical signed base-10 integer string>,exact:true}` (never a JS number, including values >2^53); `{type:"real",value:<Python shortest round-trip finite float decimal string>,exact:false}`; `{type:"text",value:<exact string>}`; `{type:"null",value:null}`. REAL means SQLite binary64 with **no certified decimal error bound**, not exact money/ratio; integer cents and counts remain exact. Reject floats promoted silently to exact integers, NaN/Infinity or blobs. Metadata explains REAL and integer division; later supported-answer validators must recompute decimal monetary/percentage claims from exact integer numerator/denominator or abstain. The Agent enriches a valid QueryResult into `ProofReceipt` with `proof_kind:"engine"|"ai_chain", ai_chain_complete:<boolean>, model:<Llama ID or null>, prompt_revision:<"m2-sql.v1" or null>, model_calls:<0|1>, agent_runtime_mode, agent_build_revision, agent_worker_version_id, agents_version`. The Agent applies the same explicit local/deployed/null/build provenance rules, reading its own `env.CF_VERSION_METADATA.id` for agent_worker_version_id and its own BUILD_REVISION; it cannot reuse Python's version UUID as its own. Only a real successful schema-valid AI planning call followed by the matching Python result has `proof_kind:"ai_chain",ai_chain_complete:true`; deployed AC-M2-02 additionally requires both runtime modes deployed and mapped actual provider receipts. Direct SQL compatibility receipts are `engine`, model/prompt null, calls 0, chain false; neither is an analytical answer. No model-invented provenance/rows are accepted. TS reads returned service bytes incrementally, aborts at 16,384 before JSON/schema parsing and treats identity/job/version mismatch as invalid output.

## Restricted transport, session and state (`m2-state.v1`)

M2 exposes only `/proof/*`, with server-side `PROOF_TOKEN` (≥32 random bytes) required as bearer header on **every** request; missing/wrong token returns access_denied without Agent lookup. Never embed this token in a query/cookie/URL/model/prompt/log/repo. Deny all Upgrade requests before Agent lookup; non-proof/native SDK/foreign Agent routes return 404. Mutations require exact same Origin as request URL, including operator CLI requests. No CORS. Responses have no-store, nosniff and no-referrer. Native `validateStateChange` must reject any source other than `server`, even if transport expands later.

Server issues 256-bit random `di_proof_session` cookie on initial authenticated GET `/proof/state`: HttpOnly, SameSite=Strict, Secure in deployed HTTPS, Path=/proof, Max-Age=604800. DO name is SHA256(cookie), derived only by the outer server; never accept Agent/session/evidence IDs as routing authority. An existing cookie opens only its own session; malformed/missing/expired cookie creates a fresh empty session rather than guessing another. Lost cookies cannot recover prior history. UUIDs identify owned jobs/receipts, never grant access. Requests to guessed foreign paths are 404; cancel IDs not matching the owned current job return uniform not_found.

GET `/proof/state` → `SessionState{version:"1",revision:<monotonic integer>,selected_source:"sales"|"support",capabilities:<["query"] or []>,history:<ordered entries>,dropped_history:<count>,job:<Job|null>,expires_at:<ms>}`. Each history entry has `id,created_at,kind:"question"|"clarification"|"failure"|"execution_receipt",source,request_id,text:<bounded string|null>,receipt:<ProofReceipt|null>,receipt_status:"not_applicable"|"retained"|"evicted"`. GET does not submit/resume work. Persist last 12 entries (question/clarification text ≤2,000 characters), most recent completed receipt only, max state 65,536 encoded bytes; remove older receipt payloads with receipt_status=evicted and null receipt, then evict oldest terminal entries before committing. Increment dropped_history only for removed entries; retained evicted-receipt markers explicitly distinguish unavailable evidence from success with inspectable evidence. No synthetic supported-answer entry.

Native `StoredSessionState` owns that projection plus private `request_journal:<last32 entries>,job_starts:<last30 epoch-ms starts within hour>,model_starts:<last12 epoch-ms starts within hour>`; the total stored object, not only the public view, obeys the state-byte cap. Public SessionState omits these journals/counter arrays. `ProofBudget` owns `{version:"1",utc_day:<UTC YYYY-MM-DD>,query_calls:<0..128>,model_calls:<0..24>}` in one server-named private DO; its narrow internal admission method consumes one query/model counter or refuses. It stores no question/source/session text and provides no user route.

POST `/proof/source` body `{version,source:"sales"|"support"}` persists selection and increments revision; active job returns busy409. Support capabilities are empty and support query is unsupported_source with zero model/query calls; never fall back to sales. POST `/proof/query` body `{version,request_id:<UUID>,question:<strict nonblank 1..2000 chars>}` starts the AI chain. POST `/proof/sql` additionally requires `sql:<strict nonblank <=8000 bytes>,max_rows:<1..20>` and supplies an explicit direct-engine proof; question is retained as operator intent, not validated meaning. POST `/proof/cancel` body `{version,job_id:<UUID>}` cancels owned active work; terminal duplicate cancellation returns unchanged owned state. Stream and cap all mutation bodies at 16,384 bytes before JSON parsing; reject extra fields. POST `/proof/reset` clears owned history/receipt/request ledger and returns a new fresh cookie; reject while active, preserving old job fence.

Successful mutations return complete SessionState: source/cancel/reset HTTP 200; new query/sql HTTP 202 after the queued job is durably committed and background execution scheduled, without awaiting the full model/tool chain. Current-job duplicate returns HTTP 202 if active, 200 if terminal. A prior duplicate with a still-retained matching receipt returns HTTP 200 state containing that receipt; otherwise return SafeError `request_outcome_unavailable` HTTP 409 with the owned journal job_id and no rerun. Failure responses are SafeError at the specified HTTP status. Invalid input/version/unsupported source refuses before creating a job/history entry; accepted downstream failures persist a terminal job and safe failure entry.

`Job` fields: `id,request_id,input_sha256,source:<frozen selection>,source_identity:<verified identity|null>,generation,phase,started_at,deadline_at,model_calls,query_calls,error:<SafeError|null>,clarification:<string|null>,receipt:<ProofReceipt|null>`. Phases are `queued→planning→executing→succeeded`, direct SQL `queued→executing→succeeded`, or terminal `clarification|failed|interrupted|cancelled`. Store a queued job and its input hash before any awaited dispatch; one active job per session. Freeze the server-verified identity once metadata arrives, before any model/query call. Keep last 32 accepted `{request_id,input_sha256,job_id}` journal entries; hash canonical `{version,proof_kind,source,question,sql:<string|null>,max_rows:<integer|null>}` with the result canonicalizer. Same ID/same input is idempotent as defined above; different input is request_conflict409. Evicted outcome produces request_outcome_unavailable, never a rerun while its ID is retained. After 32-ID eviction or reset, that ID has no idempotency guarantee; clients use a fresh UUID. Do not claim physical exactly-once execution.

Commit any phase/result only if owned job ID, frozen source identity, generation, active phase and deadline still match; recheck after every await before dispatching further work. Cancellation increments generation and atomically sets cancelled/no receipt. Startup marks persisted active jobs interrupted; expiry callback uses job ID/generation, and deadline ≥60,000 ms from start becomes interrupted. Client disconnect loses transport and work may finish if the platform keeps it alive; refresh reads authoritative state and never auto-resubmits. A late model/tool completion after cancel/restart/new job is ignored and cannot create a receipt/history success. Clarification is terminal, ≤2,000 characters, no result/no analytical prose; explicit fresh request supplies clarifying input and invokes a new bounded attempt. Same-source model context uses at most the latest four bounded history texts; no receipt may become remembered analytical truth.

Background mechanism: after persisting queued state, durably schedule the native Agent expiry callback with job ID/generation/deadline, then register `ctx.waitUntil(runJob(...))` and return 202. This is **best-effort execution**, not resumable work or a guaranteed 60-second execution window; ordinary HTTP waitUntil can terminate earlier (documented 30-second extension), and Agent/DO target behavior must be measured. The 60-second deadline is only a publication/expiry fence. If expiry scheduling fails, stop with interrupted and zero dispatch rather than returning a durable-acceptance claim. Every authorized state read reconciles an expired active job to interrupted before returning; delayed alarm delivery cannot leave an expired operation looking active. Stored session/job state is the sole outcome authority; a live promise or lost HTTP connection cannot imply success. Target probes must show a real successful queued/refresh receipt within the observed lifetime and truthful terminal interruption/no receipt for delayed/stopped background work, disconnect and restart. Unrun fault-injection or unsupported lifetime remains explicitly unverified; never infer recovery support from ordinary persistence.

Logical idle retention is seven days: authenticated access extends expires_at; scheduled expiry checks current expires_at and clears owned logical state/history/receipts/IDs, while old expiry callbacks cannot clear renewed state. Reset also clears these derivatives. Cookie loss leaves prior state inaccessible until expiry. This is application visibility/retention, not a promise of forensic removal from provider backups. Operator accepts only synthetic diagnostic input; future public chat must carry its own reviewed disclosure/retention contract. No content-capturing telemetry is enabled.

## Budgets, safe errors and critical-path recovery

One accepted job: **at most one** AI invocation and **one** query, no technical retry/replan/provider SDK retry, 60-second publication/expiry deadline with no guaranteed execution window; model timeout 30 seconds, service timeout 10 seconds. Persist model_calls immediately before invoking AI, never decrement on failure; query_calls before dispatch. Full serialized AI request ≤12,288 bytes (system/schema/history/profile/question combined), response ≤8,192 bytes, max_tokens 512, temperature 0, nonstreaming; bytes bound context conservatively and are not tokenizer/SLO claims. Model uses `@cf/meta/llama-3.3-70b-instruct-fp8-fast`, strict required-nullable `{status:"sql"|"clarify",sql:<string|null>,question:<string|null>}`: sql status requires sql only; clarify requires question only. Support object and JSON-string `response` values, reject absent/unknown shapes, extra fields, non-JSON or schema violations before tools. Never give source/question instructions tool authority; prompt authority remains server policy. No answer synthesis/Validator call in M2.

Per-session durable admission: at most 30 accepted jobs/hour and 12 AI calls/hour, rejecting excess before model/query work. `ProofBudget` admits at most 128 query attempts and 24 AI calls per UTC day across **all** proof sessions. Reserve the relevant counter before dispatch, never refund uncertain work; refuse unavailable budget service. Rotation/restart/new cookie cannot reset global counters. Direct SQL consumes no AI counter. The operator-only surface, one active job/session, total daily work caps and strict per-query resource limits bound this tiny proof; no global execution lease/wait queue or hidden retry is introduced. Terminal budget refusal is inspectable. These conservative operational caps are M2 choices under full GO, not account plan/cost estimates.

`SafeError{version:"1",code,stage:"input"|"admission"|"planning"|"query"|"transport"|"state",job_id:<owned UUID|null>,limit:<{name,maximum}|null>,provider_reason:<"daily_free_allocation"|"account_limited"|"out_of_capacity"|"unknown"|null>,automatic_retry:false}`. Allow codes: invalid_input/unsupported_version (400), access_denied (403), not_found (404), unsupported_transport (400), busy/request_conflict/source_mismatch/request_outcome_unavailable (409), unsupported_source/unsafe_query/invalid_query/execution_limit/invalid_result (422), result_limit (413), budget_exhausted/model_quota (429), model_output_invalid/python_output_invalid (502), model_unavailable/python_unavailable/runtime_incompatible (503), interrupted/cancelled (409). Persisted terminal errors use the same classified fields; GET state still returns 200. Labels and corrective actions map via UX ST-1–10, never raw exceptions. Manual new requests are possible after owned terminal-state recovery and remaining admission budget; unknown timeout outcomes have no automatic retry. Known malformed/version/support refusals make zero calls. Never invent a reset time or substitute a default/fabricated result.
