## Sales fixture, provenance and strict loading

Provenance: the 24 rows below are newly authored synthetic demonstration data, not observations of a real business. Grain is one net sale/return line; IDs are unique line identities, not orders/customers. All fields are required and non-null. There is no join contract to the support customer labels or products, no customer master and no inferred causal relationship. Different unit prices are permitted; revenue is not derived as units multiplied by a universal price. No profit, tax, currency conversion or gross-sales measure is provided.

| Field / storage | Exact meaning and parser bound |
| --- | --- |
| `sale_id` / TEXT | Canonical `D[0-9]{3}`, unique in the demo; exact fixture order retained. Proof keeps its existing S IDs. |
| `sale_date` / TEXT | Canonical `YYYY-MM-DD`, valid Gregorian UTC calendar-day meaning; no time/offset inference. Filtering periods are `[start,end)`; explicit months January–March 2026. |
| `customer`, `region`, `product` / TEXT | Case-sensitive synthetic dimensions, not stable external identifiers; nonblank, no leading/trailing whitespace, Unicode controls or normalization/coercion; each ≤64 UTF-8 bytes. The approved bytes are ASCII. |
| `units` / INTEGER | Signed net units: negatives are returns, zero valid. Canonical decimal `-?(0|[1-9][0-9]*)`, disallow `-0`, whitespace, plus sign, exponent/decimal/coercion; signed int64 range. |
| `revenue_cents` / INTEGER | Signed net USD cents: negatives are returns, zero valid; same strict int64 parser. Exact monetary measure, not float dollars. Sign disagreement with units is unsupported for this fixture; zeros must be paired. |

File is UTF-8 without BOM, LF only, final LF required. Header is exactly the seven column names below in that order, without duplicates/extras. Read at most 65,537 bytes and reject above 65,536 before decoding; cap 256 records, 2,048 bytes per physical line, seven cells per row and 256 bytes per decoded cell before typed conversion. These are loader ceilings, not permission for arbitrary data: production loading also requires exact manifest size/hash/count. Use strict CSV parsing; reject blank lines, multiline cells, malformed quoting, invalid UTF-8, missing/extra cells, unsupported nulls, duplicate IDs, bad dates/integers or invalid field bounds. Permit CSV syntax only where it yields the declared seven cells; do not trim, normalize or repair input. P1's new loader returns immutable typed source/rows/schema/meanings, with no new profile; the old `SalesFixture` and its minimal profile remain unchanged.

## Profile receipt (P2/P4; DEC-M3-01)

Local strict `DataProfileV2` contains exactly `version="2"`, full `source`, `schema_revision`, `profile_revision="m3-profile.v1"`, `fields`, `record_count`, nullable `range_start/range_end`, `dimensions`, `measures`, `omissions`, actual implemented `capabilities`, `analytical_validated=false`. Each field is `{name,sql_type:"TEXT"|"INTEGER",nullable:false,meaning,null_count}` in declared source order; meanings use this contract, every null_count is exact. Sales range values are calendar dates; support values are canonical UTC timestamps. Counts are bounded JSON integers ≤256; monetary/unit statistics use canonical decimal strings with `exact=true` and explicit `unit` (`net_units`/`USD_cents`). Only `count,min,max,sum` are supported in this policy revision; no averages, percentages, inferred anomalies or model prose. Arithmetic uses Python integers; out-of-int64 statistics refuse with `invalid_result` rather than silently approximate. Source bytes/meaning identity accompany every profile.

Each dimension is `{field,distinct_count,values,omitted_value_count}`: sorted code-point ascending exact labels, at most eight values per declared dimension, unique count and omitted count refer to the whole validated source. Dimension order is customer/region/product for sales, channel/customer for support. Each measure is `{field,unit,count,min,max,sum,exact:true}`; sales measure order is units/revenue_cents, support measures is empty. Fixed `omissions` detail labels are `bulk_rows`, `row_samples`, `distributions`, `uncomputed_statistics`; record omitted dimension values by count, not an unbounded list. Profiles never contain support message text or bulk rows. No source is sampled to compute the reported counts/statistics. Serialize the whole profile to ≤4,096 UTF-8 bytes; oversize refuses `result_limit`, with no silent removal of fields. Repeated canonical profile content is deterministic; runtime envelopes are separate. Valid empty approved test data produces count zero, null ranges/min/max and zero sum; packaged manifests are nonempty, so an empty production fixture fails loading.

Sales capability `query` appears only after reviewed P2 engine integration, support `search` only after P4; loading/profile existence never grants a tool capability. Generic query integration keeps `main.sales`, existing declared columns/function allowlist, `m2-sqlite.v1`, 20-row/16-column/16,384-byte result limits, progress/deadline/heap controls, unchanged actual SQL/hash/source receipt and whole-result refusal. It must explicitly select one approved fixture through its full identity; no concatenated cross-source data or SQL rewriting. Queries and monetary exactness remain separate from semantic approval.

## Support loading and targeted evidence (DEC-M3-02)

Support provenance is the exact 16-message synthetic reference file above, not real tickets. Strict JSONL has one object per LF-terminated physical line, UTF-8 without BOM/CR, no blanks/duplicates/extra fields, JSON constants NaN/Infinity or coercion. Apply the sales byte/row/line ceilings before parsing. Fields: `message_id` canonical `M[0-9]{3}` unique; `timestamp` canonical valid UTC `YYYY-MM-DDTHH:MM:SSZ` with no fractional seconds/other offset; `channel` and `customer` nonblank case-sensitive labels ≤64 UTF-8 bytes without surrounding whitespace/controls; `text` nonblank exact source string ≤500 UTF-8 bytes, allowing spaces/punctuation but no control characters. All required/non-null. Object duplicate keys must reject. Preserve strings exactly, including source quotes; mentions are untrusted content, never instructions. P3 verifies exact 3,091-byte/hash/16-row manifest; loaders never follow reference paths at runtime.

`SearchRequestV2={version:"2",source,query,channel:null|string,customer:null|string,start:null|UTC_timestamp,end:null|UTC_timestamp,max_hits:1..5}` is strict and ≤2,048 UTF-8 bytes; query is nonblank ≤128 UTF-8 bytes; non-null channel/customer obey their source label bounds. All strings are Unicode scalar values (no surrogate code points), and control characters mean Unicode categories Cc/Cf. Filters are exact case-sensitive equality and UTC `[start,end)`; start must precede end when both exist. Unknown filter labels are valid no-hit searches, not schema errors. Tokenization maps ASCII A–Z to a–z then extracts distinct `[a-z0-9]+` tokens, sorted ascending: 1–8 tokens, each ≤32 characters; refuse punctuation-only/excessive input. No stop-word removal, stemming, phrase, substring, accent/non-ASCII normalization or semantic matching. Match at least one distinct token in the message's similarly tokenized text. Score is integer count of distinct query-token matches. Sort score descending, timestamp descending, message_id ascending. Scan every approved message satisfying the filters, never fetch external data.

`SearchReceiptV2={version:"2",source,schema_revision,search_policy:"m3-lexical.v1",request,scanned_count,matched_count,returned_count,omitted_hit_count,hits,coverage:"targeted_lexical_search",limitations,analytical_validated:false}`. Counts describe only this lexical operation, never issue prevalence. `scanned_count` is filter-eligible messages; each hit is `{message_id,timestamp,channel,customer,score,matched_tokens,quote}` with `quote` equal to the complete original text, untrimmed and unmodified. Keep ≤5 hits and ≤8,192 UTF-8 bytes for the whole receipt; overflow refuses, with no extra truncation. `omitted_hit_count=matched_count-returned_count`; this deliberate top-hit selection is inspectable even when zero. Always include two fixed limitations: "Targeted lexical examples cannot establish whole-corpus trends, prevalence or absence." and "No hits means this lexical query found no matching messages in the declared filtered scope." Do not produce aggregate theme facts or affirmative absence statements. A later citation may resolve only to a returned message and an exact nonempty substring of its quote; citation validation is a separate P6 contract.

Profiles/search each operate on ≤256 validated records, with a 100-ms monotonic execution deadline checked per record and before success; expiry refuses `execution_limit`, no partial receipt. These are defensive application ceilings, not measured latency promises. No retries, caching across mismatched identities or hidden expansion of search is allowed. Hashing/parsing uses the bounded fixture; deployed total-runtime/FFI behavior still needs fresh evidence.

## Safe errors, private service evolution and recovery

Local loader errors retain safe `fixture_missing`, `fixture_invalid`, `source_mismatch`; add `unsupported_source` only for catalog resolution. Missing/unreadable approved file and invalid bytes/manifest/parser have no paths, cells or raw exceptions in error text. Tool errors: `invalid_input`, `unsupported_version`, `unsupported_source`, `source_mismatch`, `invalid_result`, `execution_limit`, `result_limit`, `runtime_incompatible`. No arbitrary caller-controlled text in errors. Logs contain only component/operation/safe correlation ID/code/bounded sizes/counts/revision IDs; never source text, query/question, model/provider body or credentials.

Preserve existing service-v1 `/health`, `/metadata`, `/query` and strict consumers unchanged. P7 may add private `/v2/catalog` GET, `/v2/profile` POST, `/v2/query` POST and `/v2/search` POST after their tools merge. POST profile body is `{version:"2",job_id:<UUID>,source}` ≤1,024 bytes; search adds job_id to SearchRequestV2, ≤2,048; query uses `{version:"2",job_id,intent:<existing SqlIntent>}` ≤16,384. All requests/results are strict DTOs; unsupported/extra fields refuse. Catalog returns registered identities/schema/revisions and actually implemented capabilities, no filesystem paths, ≤4,096 bytes. Profile/search success envelope is `{version:"2",job_id,payload:<typed receipt>,payload_sha256,runtime:<existing RuntimeInfo>}`; profile payload ≤4,096, search payload ≤8,192, whole envelope ≤16,384 bytes. QueryResultV2 changes outer version to "2" and accepts only reviewed registry identities/schema revisions; retain all existing exact Cell/result controls and full-envelope cap. Version-1 proof DTOs must not be broadened.

`payload_sha256` hashes the payload's canonical JSON: recursively key-sorted, UTF-8, no ASCII escaping, separators comma/colon without whitespace, no NaN/Infinity. The service computes it; consumers validate actual content and identity, never authorize from a hash alone. UUID/runtime are outside deterministic payload. Stream request bodies to their declared cap before parsing, bound returned bytes, and use the existing ten-second private-binding timeout with no retry. Private v2 errors have `{version:"2",code,stage:"input"|"profile"|"query"|"search"|"transport",job_id:UUID|null,automatic_retry:false}`: 400 invalid_input/unsupported_version, 422 unsupported_source/invalid_result/execution_limit, 409 source_mismatch, 413 result_limit, 503 runtime_incompatible. Loader failures map to runtime_incompatible; retained query errors preserve existing status semantics. Untrusted malformed output is not a successful receipt. Runtime provenance retains executing Worker version UUID versus separately recorded provider deployment IDs and real reviewed build revision; local nullable provenance never proves deployment.

No public route, native Agent handler, client-selected path, bearer/cookie forwarding or model integration is added in M3. Deploy v2-capable tools before any reviewed v2 consumer; retain v1 during the transition. P1–P4 remain independently usable offline; service compatibility and deployed checks cannot be claimed from local build/upload alone. Roll back new tools to an identified reviewed version or disable new capability; preserve old receipts/reference resources. Failures require explicit corrected input/new owned call, with no automatic retry or fabricated empty success.
